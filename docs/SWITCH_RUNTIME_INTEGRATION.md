# NGR Switch runtime integration

Status: **integration started; not yet build-verified or playable**.

## Donor revision and what is actually reusable

- Donor: https://github.com/shirai91/nx2android
- Pinned audit revision: `f32b3d563f0615d0e825747285d4e38d780e4ebb`
- Architecture: `docs/ARCHITECTURE.md`
- Runtime build: `nxnative/dm/android/build.py`
- APK writer: `nxnative/dm/android/apk/mkapk.py`
- Port pipeline: `porter/pipeline.py`

The donor's APK is not the runtime itself. Its per-title native runtime is `libdmhost.so`, produced by `dm/android/build.py --game <16-digit-title-id> --ndk <NDK> --release --lib`. The APK writer wraps that library in a minimal `android.app.NativeActivity` package and adds launcher metadata/assets. The game data is separate from the APK and is read from the app's private files area.

NGR must therefore keep one installed application and store each prepared title under:

```
files/switch-ports/<TITLE_ID>/
  manifest.json
  runtime/libdmhost.so
  mods/
  RomFS/
  aoc/
  sysdata/
  shaders.dmsv
  env.txt
  settings.txt
  nx2a-data.json
```

Only files required by a particular game's profile are present. User game data, firmware and keys are never copied into the repository or NGR APK.

## In-process NativeActivity dispatch

A donor `libdmhost.so` exports `ANativeActivity_onCreate`. It is compiled with a title-specific `game_profile.h`; it is not a universal runtime and must match the prepared data pack.

NGR now has the first loader and runtime-build adapter slice:

- `native/ngr-runtime/src/switch_activity_loader.cpp` exports the NativeActivity entry point registered by NGR's manifest.
- The loader reads the runtime library path from the activity intent and validates a per-title private root for saves and temporary files.
- It accepts only a canonical regular file under NGR's private `files/switch-ports/` directory and requires the donor runtime filename `runtime/libdmhost.so`.
- It loads the selected per-title library with `dlopen`, resolves its `ANativeActivity_onCreate`, and forwards the existing activity lifecycle to it. The library handle is retained for the activity lifetime.
- `SwitchRuntimeLauncher.kt` validates the 16-hex title ID and delegates to `SwitchRuntimePackageVerifier`, then launches the in-package NativeActivity with the path extra.
- `SwitchRuntimePackageVerifier.kt` checks the pinned donor revision, title ID, ABI, entry point, non-APK output flag and SHA-256 of `libdmhost.so` before launch.
- `tools/switch/build_runtime.py` invokes the donor's real `dm/android/build.py` for a matching title profile, validates the resulting AArch64 NativeActivity library and writes it to the NGR per-title package layout with a build receipt. It deliberately never calls `mkapk.py`.
- `tools/switch/port_game.py` now orchestrates the donor's actual `python -m porter port` pipeline for a user's source folder and `prod.keys`: extraction, NSO rewrite, shader conversion, profile-specific host build and data-pack creation. It applies the reviewed patch `patches/nx2android/0002-ngrn-build-without-per-game-apk.patch`, which makes the donor pipeline skip only the per-title APK step while retaining host and data outputs. The wrapper then assembles an importable folder containing `runtime/libdmhost.so`, `data/` and `runtime-build.json`; it does not copy keys into that folder.
- `.github/workflows/switch-runtime-smoke.yml` fetches the pinned donor revision and builds a profile-only smoke runtime; its artifact is not a playable game and contains no game data.
- The app manifest registers `android.app.NativeActivity` using the loader library. No game-specific APK is installed or generated by this launch path.

This is an integration seam, not yet proof that the donor NativeActivity can be forwarded safely on all Android versions. CI must compile it, then a synthetic NativeActivity fixture and physical-device smoke test must verify lifecycle callbacks, surface recreation, pause/resume and clean shutdown. A real title must not be marked playable before that evidence exists.

## Port preparation pipeline

NGR's desktop-assisted adapter now calls the donor pipeline rather than reimplementing its proprietary-format parsing. The donor architecture separates host-independent preparation steps from Android runtime packaging:

1. Scan NSP/XCI and optional update/DLC; decompress NSZ/XCZ.
2. Extract ExeFS/RomFS with the pinned nx_extract/.NET/LibHac toolchain and user-provided `prod.keys`.
3. Rewrite NSO/NRO with `patch_nso.py` and the exact title/build profile.
4. Split shaders and build the Maxwell-to-SPIR-V translator output.
5. Build the title-specific Android host with `dm/android/build.py`.
6. `port_game.py` skips `mkapk.py`, then assembles an NGR Switch Port Package (`runtime/libdmhost.so` + donor data pack + runtime receipt), **not an APK**.
7. Verify all files and profile fingerprints; atomically register the title in the NGR library.
8. Launch the title through the NGR NativeActivity dispatcher.

The nx2android CLI pipeline remains a desktop preparation tool and depends on Python 3.11+, its Python modules, .NET 10, NDK r27c, game-profile support and user-owned keys. `port_game.py` expects a pinned donor checkout and an `NX2A_HOME` containing the donor's configured NDK/.NET tool paths. The NGR Android source worker still only stages source files; it does not execute this Python/.NET toolchain on-device. The current adapter is desktop-assisted and its output is imported into NGR with the Switch Port folder picker. Moving the complete pipeline onto Android is a separate effort.

## Compatibility and security rules

- The title ID and build ID must match a donor game profile. Do not guess profile offsets or apply a profile to another game/update.
- Require ARM64 Android output and the donor's Android API/GPU requirements; nx2android documents Adreno/Xclipse and BC texture support, not Mali/PowerVR.
- The profile header hash, rewritten module hashes, shader bundle version and runtime build hash must be recorded in the NGR package manifest.
- Never execute an unverified library. Validate manifest schema, file inventory, hashes, profile/runtime ABI and canonical paths before launch.
- Keep `prod.keys`, title keys, firmware, NSP/XCI files and game assets out of Git, CI artifacts and logs. Redact key values and sensitive paths.
- Preserve `nxnative/LICENSE` and every third-party license/notice. The nxnative core is MIT, but LibHac, Ryujinx shader translator, SPIRV-Cross, glslang, deko3d-derived code, zstd, libvpx, Capstone, LZ4 and other dependencies retain their own licenses. A donor-level MIT label does not make every dependency MIT.
